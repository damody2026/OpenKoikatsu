### 2.2 voice_extract 的實際結構

- `comm_lines.json`：clip key → file、text、assetbundle、src。18847 筆紀錄。
- `translation_comm/comm_zh.json`：18752 個翻譯 key；與上述紀錄 key 相交且非空為 18645 筆。這不等於每筆都已完成翻譯品質驗收。
- `tools/audio_index.json`：資源 bundle、取樣率、聲道、長度等。
- `audio/<personality>/<kind>/<clip>.ogg`：原日文音訊；會話參照含 adv 與 adm。
- `cn_audio_comm/<personality>/<kind>/<clip>.wav`：中文會話音訊。
- `manifest_adv.json`：有劇本位置、角色、原文、翻譯、音訊等欄位，可補充事件內容。
- `translation_comm/clip_index.json`：翻譯排序索引，不能當遊戲節點或關係 ID。
- `h_data.js`、`manifest_h.json`、`audio/*/h`：屬另一組內容。這次不把性愛場景喘息或動作音訊當一般街頭會話。

本次以 comm_lines 的 file 拆分多段參照，再經 audio_index 解析實際路徑：202 筆紀錄有多段語音；18003 個參照有索引，17823 個參照找到原 OGG，17823 個找到中文會話 WAV，涉及 41 個性格資料夾。以上是「參照數」，不是去重後檔案數，也不是三類話題的覆蓋率。未索引項目包括需另解的稱呼等情況，需在正式匯出時分類。

**關鍵缺口：** comm_lines 是扁平文字／語音清單，不包含完整 conditions、favor、lewdness、anger、選項與上下文連接。實作必須匯出原 Communication、Topic、關係門檻、性格與聲音映射資料，不能直接把扁平清單當完整對話樹。

## 4. KKS 風格對話方式

### 4.1 開場與話題選單

靠近可交談 NPC 顯示姓名與提示，按 E：保留 NPC → 平順停止 → 面向玩家 → 開場招呼 → 三類話題選單。

| 類別 | 內容方向 | 狀態影響 |
|---|---|---|
| 日常 | 生活、食物、興趣、街區見聞、近況 | 好感、興趣紀錄、再次交流內容 |
| 戀愛 | 感情觀、關心、稱讚、關係與告白相關交流 | 好感、關係事件；依熟悉程度接受或婉拒 |
| 性愛話題 | 私人親密話題與對方態度 | 親密話題接受度／原 lewdness、好感、拒絕或尷尬狀態 |

流程以原資料為準：有些主題直接得到 NPC 回應，有些含選項、條件分支或後續追問；不強迫每句都製作三選一。補充話題列表、告白、道別等命令要有清楚入口與關係條件。

第一版三类選單完整保留。不可用項目可顯示原因；資料有拒絕回應的情況允許提出後婉拒，不能用高好感一律跳過原回應條件。

### 4.2 每次交流的狀態機

`自由活動 → 選取候選 → 預約 NPC → 停靠與轉向 → 開場 → 話題選擇 → 回應準備 → 語音/表演 → 結果提交 → 下一話題或道別 → 恢復活動`。

- 只對載入與淡入完成的角色顯示有效提示。
- 候選搜尋約 2.5 公尺；依距離、鏡頭方向、視線遮擋排序，可切換候選。
- 對話只占用當前 NPC，其他四人繼續走停。
- 字幕、語音、選項、表演分別有生命週期，避免文字消失後還播放舊音訊。
- 每次結果用唯一 transaction ID，只能提交一次。
- Esc、角色移除、換場景、載入失敗、音訊失敗會取消 pending 工作、釋放占用、恢復嘴型和活動。
- 台詞跳過不是重複提交；跳過與中斷取消的效果語意由節點定義。
- 後台準備動作時仍顯示正常待機；未就緒的 gesture 不能讓對話 UI 卡死。

### 4.3 第一版內容驗收量

- 五張不同女角 APNG，盡量涵蓋不同且有會話資料的性格。
- 每張卡三類話題各至少三條可到達且有匹配音訊的回應，另含開場、道別與至少一個拒絕／負面回應。
- 每種原始結構至少驗證一個：直接回應、條件分支、選項、多人名／稱呼、多段語音。
- 小樣本驗收不表示只支援五種性格。內容索引、映射與缺失處理要能接受後續任意 APNG。
- 不硬改卡片性格湊資料；缺失性格列為覆蓋缺口，使用經聲音映射確認的合法共用回應或明確文字回退。

## 5. 語音／字幕／分支資料建置

### 5.1 共用資料匯出

新增通用匯出工具，讀取原作共用資料與 voice_extract，不接受特定角色卡作為建置輸入。

建置步驟：

1. 匯出會話群組、命令、性格、關係階段、priority、conditions、回應與選項結構。
2. 保存原始好感／親密效果、anger、topic、姿勢、表情、eyes/neck look。
3. 匯出 StepUpData 與 personality → voiceNo 映射，包含負編號／固定角色的處理。
4. 以來源 bundle＋clip＋聲音 profile 建立唯一 voice key；不能只以 sun/com 前綴或文件排序作為類別判斷。
5. 用 comm_lines 與 manifest_adv 對照原文，再以 comm_zh 對應中文；保留 [P名]/[H名] 等名字占位符。
6. 拆解多段語音與 callName，依原次序處理，不隨機選最後一段。
7. 實際檢查中文、日文檔案存在、可解碼、時長與聲道；建立缺失和衝突報告。
8. 中文 WAV 在共用資產準備階段轉為遊戲支援的壓縮格式，避免 runtime 一次讀入整套 WAV。保留來源 hash、轉碼設定、輸出 hash。
9. 輸出共用 catalogue、會話 graph、規則表、翻譯表與 audio manifest，記錄版本。

工具不執行 voice_extract 內的指令文件或啟動其翻譯／TTS worker；它们是來源資料，相關檔案只按需求讀取。不修改原目錄、不重新生成全套中文聲音。

### 5.2 Runtime 選取與播放

1. APNG 性格與聲音資料 → 經匯出映射找 dialogue profile 和 voice profile。
2. 對話命令＋關係階段＋旗標 → 篩選可用候選，按原規則／權重選取。
3. 節點確定後預載當前及少量下一步可能回應，背景解碼。
4. 音訊、字幕與所需基礎表演可用後開始；嘴型由實際音訊時鐘驅動。
5. 中文缺失 → 同一台詞的日文；兩者皆缺 → 正確文字並報告，不換成無關台詞。
6. 未錄製的玩家台詞可以無聲；NPC 的正常測試台詞必须播放對應語音。

現有 runtime manifest 語音上限 256、VoiceId 以檔名識別，不能直接塞入約一萬多段會話音訊。需要改為共用 catalogue 的按需 lookup 和有界解碼快取。多段音訊排程要支援取消 generation、清理舊工作和順序播放。

聲音音高／語速依卡片屬性處理並與嘴型時鐘同步。語音與字幕的不同長度需以音訊結束、手動跳過和文字閱讀狀態協調，而非固定每句三秒。

### 5.3 記憶體與檔案

- 共用音訊資料包不屬於每張卡私人 GPU pose cache。
- 初始解碼 PCM 快取建議 64 MiB，採最後使用時間淘汰，播放中的音訊不可移除；正式 profile 後調整。
- 對話 catalogue 只載小型索引和需要的性格資料，不啟動時讀入全部音訊。
- 本機開發可讀 voice_extract；正式遊戲使用經匯出的相對路徑共用資料包，不能依賴 C 槽固定路徑或 KKS 安裝目錄。

- 每個 NPC 獨立保存 favor、關係階段、親密話題接受度（對應 lewdness）、話題記憶、交談額度和事件旗標。
- 優先保留能匯出的 KKS 原資料門檻與效果；之前提案的 20/50/80/100 只是初始建議，不在未驗證下當原作數值。
- 段階好感和總歷史分開：原作升級重設 favor 時，總互動紀錄仍保留，UI 顯示當前階段進度與關係名稱。
- 朋友／戀人等重要階段由事件推進，不僅滿分就自動成立。
- 偏好、原始條件、各選項效果與機率以資料驅動。無法在第一版支援的原作條件建立明確 support matrix；不默默把未知條件當 true。
- 原作旅館、祈願、其他世界設施相關修正不在第一版新增。採有文件紀錄的中性值，相關事件在街區禁用；不能宣稱完全重現全部 KKS 平衡。
- 交談額度初始可沿原資料；日常、戀愛、性愛命令的額度消耗照驗證結果執行。
- 為避免刷分，加入已聊話題紀錄、原可用次數與明確冷卻。若新增額外遞減規則，與原作規則分開標示並可配置。
- 用完額度仍可打招呼、查看關係與道別；不能讓 NPC 失去正常互動。
- 私人話題回應可以正面、害羞、拒絕或終止；親密接受度與好感獨立，不能強行綁為同一數字。
- 關係變化不得重建人物網格、材質或整份姿勢庫。

## 7. NPC 活動、動畫與 GPU 整合

### 7.1 街道行為

活動狀態：Walking、Waiting、Looking、Resting、Reserved、Talking、Recovering。

- 導航資料只由自製街區產生，目的地與活動點可配置。
- 玩家使用碰撞移動；NPC 尋路只在目的地改變、路徑失效或卡住時執行。
- 設局部避讓、停靠點、卡住恢復與活動點占用，防止五人集中在出生點或互相穿越。
- 交談前保存目的地與原活動，结束後恢復或重新選取，不使用一卡一例外。
- 決策分批更新，但動畫仍保持 60 Hz。不同走法與私人骨架独立，擴充不假設同 pose。

### 7.2 Runtime 渲染接口

目前 FScene 自行控制 index0、鏡頭和正弦路線。需要增加外部控制模式：

- 查詢角色就緒、可見、錯誤、穩定 ID、metadata 與 transform。
- 街區系統提交角色 transform、移動速度與活動意圖。
- 控制／預約單名 NPC，切換待機、步行與對話動作。
- 以 actor handle＋generation 保護重載後的命令，不能只相信名單索引。
- 原 CrowdRoom 不啟用外部模式，保持既有操作和 profile 路徑。

### 7.3 表演

- 初期完整支援站立、聆聽、說話手勢、點頭／搖頭與原可用表情。
- 嘴型依音訊 render clock，不用隨機 sin 動嘴代替真語音。
- 視線／頭部追蹤只對當前交流角色工作，保留角色自己的骨架映射、飾品和物理。
- 既有額外 action 串流是單 StreamActor，需要改成有界多角色 slot／排程，至少支援男角和女角同時表演。
- 對話常用 gesture 在靠近候選時背景預暖；不替五人／未來百人預載全部話題全部表演。
- 缺失動作保持正常站姿並報告；聲音和文字依然正確。不得套不匹配骨架造成臉／頭髮爆炸。
- 取消播放需同時處理排隊動作、已解碼音訊、正在播放音訊與嘴型復原。

## 8. Runtime 載入與身分存檔

### 8.1 載入順序

街景和男角 → 附近 NPC → 當前候選／交談者必要語音與表演 → 其他 NPC → 近期可能需要的額外動作。

保留現有 staged GPU upload、背景工作、距離優先與逐名 3 秒淡入。第一版只載五張女卡和一張男卡，額外動作不得阻塞進場。

全員 ready 定義包含 mesh/material/private pose 可渲染與可以正常進入交談；語音按需讀取，不要求整套語音庫載入才算 ready。

### 8.2 身分

- 不以檔名、路徑或名單索引識別人物。
- 保存 world ID、player ID、NPC persistent ID、卡片內容指紋與資料版本。
- 同一卡片搬家或改名仍保留關係；不同卡片同名不能混在一起。
- 內容相同的卡預設視為同一身分；修改卡片後需要可追溯的重新關聯流程，不能假稱 hash 自動知道是同一人。
- APNG 名稱、性格、性別等在背景純資料解析；禁止在每幀或搭話時同步重讀整張卡。

### 8.3 存檔

保存關係、favor、親密接受度、事件、已聊話題、冷卻、交談額度、遊戲日與必要 NPC 活動狀態。

存檔独立於 APNG；原卡不回寫遊戲關係。採版本化 SaveGame／序列化格式、暫存後替換和上一版備份。每次結果唯一 transaction，保存重試或重新載入不重複增加好感。對話正在播放時存檔保存已提交的狀態，讀檔恢復到可安全互動的待機，而不是重播未完成副作用。

## 11. 完整驗收矩陣

### 功能

- 五名女角全可見、可交談，男角可移動，其他 NPC 在交談時繼續活動。
- 日常、戀愛、性愛三類均可進入；條件分支與拒絕正常；高好感不跳過所有條件。
- 正確處理原作多段語音、稱呼、未知性格與沒有錄音的玩家文字。
- 好感／親密值／關係／交談額度計算可重現；重複點擊、Esc、跳過、存檔重試不重複提交。
- 動作和音訊準備延遲、失敗、角色移除、换場景都可恢复操作。
- 存檔重啟、卡片改名／搬移／重排序、不同卡同名都不錯配。

### 聲音與外觀

- 逐條記錄 node、性格、voice profile、原 bundle/clip、字幕、語音 path/hash、fallback 原因。
- 取樣人工聽對三類話題，確認文字語意與音訊一致，不只以檔案存在當通過。
- 記錄音訊開始、mouth 更新、結束、取消與恢复；多段間隙與嘴型正確。
- 在實際街區相同鏡位／相位對照 CPU/GPU，檢查臉、眼、手勢、飾品、衣物、色彩、陰影與淡入。
- 鏡頭有牆壁與路人遮挡時可用，不暴露未就緒角色或失去五官。

### 效能

- 第一版以六個角色（男角＋五名女角）測試，不冒充百人街區結果。
- 分開記錄冷／暖啟動、首個可操作時間、各角色 ready 時間、全部可交談時間，以及一次首次／快取命中對話準備時間。
- 正式 Development 在自由行走、五人同框、交談近景、背景載入＋交談、切話題／gesture 情況測平均、P95、P99、最大幀時間和超 8.33 ms 比例。
- 分列 Game、Render、RHI、GPU，不把管線時間相加，也不把準備時間當 FPS。
- target frame 8.33 ms；60 秒全員就緒；播放中的解碼和 action admission 不造成長幀尖峰。未達標必須顯示實際值和瓶頸，不以平均值掩蓋最大值。
- GPU budget、pose disk LRU、音訊快取分開量測；交談十次後記憶體不持續上升。
- 至少三次同配置可重現 profile，记录背景負載，不接受其他重工作並行的數字當正式結論。

目前百人房間最近紀錄 R1152：暖快取 all-ready 70.934 秒，loading mean 5.19489 ms、P95 7.68820 ms、max 86.844 ms。這不是新街區基準或穩定 120 FPS 證明；新場景需重新測量。
