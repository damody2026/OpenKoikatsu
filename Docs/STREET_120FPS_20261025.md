# 街區 120 FPS 優化（E 組，2026-10-25）

目標：使用者的電腦同時開著其他程式（另一個街區遊戲、Unreal Editor）時，街區仍維持 120 FPS 以上。

## 量測方式

- 打包版 `StreetSocial.cmd` 的 stage，1600×900 視窗，控制埠 47970。
- 依序導航到學生餐廳、圖書館、女生宿舍，每處 40 秒，每秒讀一次 `/fps`（`fps`、`game_ms`、`render_ms`、`gpu_ms`）。
- 卡頓用 `t.HitchFrameTimeThreshold 12` 加 `stat dumphitches`，看超過 12 ms 的幀落在哪個 `STAT_Street_*`／`STAT_OKCrowd_*`。
- 設定開關在遊戲內交替切換（A/B/A/B），避免把其他程式的負載變化當成效果。
- 細部用 Unreal Insights（`trace.file <檔> cpu,frame`，分析後刪除 trace）。

## 改動與效果

| 改動 | 位置 | 效果 |
|---|---|---|
| 建築模型由 ProceduralMeshComponent 改成執行期 `UStaticMesh` | `OKStreetSocialOuting.inl` `OKStreetFreezePlaceMesh` | 39 個模型（190 萬三角形）不再每幀走 dynamic mesh 路徑；屋頂與各樓層仍各自一個元件，可照舊隱藏。平均 129 → 161 FPS，宿舍 116 → 155，整段沒有低於 120 |
| 關閉硬體遮擋查詢 `r.AllowOcclusionQueries 0` | `OKStreetSocialScene.cpp` 畫質設定 | render thread 每幀約 5 ms 在等上一幀的遮擋結果（另一個遊戲共用 GPU 時更久）；宿舍 A/B：127 → 150、151 → 177 FPS，GPU 多約 1 ms |
| 關閉 contrast-adaptive shading | 同上 | 128 → 132 FPS |
| 立繪擷取限 30 Hz（換說話者時立即擷取） | `Tools/ok-story/src/portrait.rs`、`tuning.rs` `capture_hz` | 不再每幀多畫一次場景 |
| 自動存檔改在背景複製；ok-mind 存檔只排入佇列，背景執行緒等寫完再複製（`okm_save_queued`／`okm_flush`） | `OKStreetSocialSaves.inl` `SaveToSlot(...,Background)`、`Tools/ok-mind/src/lib.rs` | 自動存檔佔 game thread 479 ms → 12 ms（其中 ok-mind 50 → 5 ms），約 120 ms 的複製在背景 |
| 底部對白／提示改綁定狀態 | `OKStreetSocialScene.cpp` `OKStreetDigestMessage` | 走過人身邊時提示換字不再重建整個 UI（一次約 10 ms） |
| TTS 伺服器探測只在提示文字變了才重建 UI | `OKStreetSocialVoice.inl` | 伺服器啟動中每 2 秒一次的重建消失 |

實測（另一個街區遊戲同時開著，Look15E2）：三處平均 183 FPS（餐廳 177、圖書館 179、宿舍 194），120 個一秒樣本中 118 個 ≥ 120。

## UI 分區重建與存檔序列化（2026-10-25 下午，協調者派工）

量測：同一路線（學生餐廳 → 圖書館 → 女生宿舍、叫三月七過來、E、Esc），`ok.Street.LogUiRebuilds 1`。

| | 重建次數 | 單次耗時 | 主要來源 |
|---|---:|---:|---|
| 之前（Perf25cE） | 31 | 8.5～20 ms | 走路拾取話題的提示、開始／結束導航、進出商店 |
| 之後（UiRegions1E2） | 20 | 5～8 ms（商店 0.1～0.5 ms） | 對話中的面板操作 |

- **外殼只建一次**：版面、小地圖、大地圖、時鐘、床、電梯列、提示角、每個區塊的容器在 `RebuildUI` 第一次（或換語言，`OKStreetUi::Shell`）時建好，之後不再從 viewport 拿掉重加。
- **分區重建**：`RefreshUI(OKStreetUi::Right|Shop|Debug|Bottom|History|Apps)`，預設全部（不含外殼）。進出商店只重建 Shop；點聯絡人只重建 Right|Debug；歷史視窗開關只重建 History。
- **改成綁定狀態**：導航列與取消鈕、聯絡人提示、歷史按鈕文字、提示角、大地圖顯示，開始／結束導航、開關大地圖、走路拾取話題都不再重建。
- **存檔序列化移到背景**：`CommitStore` 等背景存檔原本在 game thread 把整個 store 序列化成 JSON（每次 4～6 ms，關係／相遇規則的 6～11 ms 卡頓大多是它）；改成 `OKStreetAtomicSaveStoreAsync`：game thread 只複製 store（`STAT_Street_SaveSnapshot`），存檔工作序列化並寫檔，同一個檔案排著的舊內容由新的取代。拾取話題也改走這條（原本每拾取一次同步寫檔）。需要「寫成功才生效」的交易式存檔（對話結果、關係確認）維持同步。
- **建築 static mesh 的 UV 密度**：執行期建的 `UStaticMesh` 材質槽補上 `UVChannelData`，修掉每次開場 12 秒的 ensure 卡頓（見 ERROR_LOG）。

## 排程、路線、群眾更新（2026-10-25 傍晚）

量測腳本：閒置 60 秒 → 時鐘跳到中午、傍晚（所有女主同時換時段）→ 學生餐廳、圖書館、女生宿舍 → 叫三月七來聊一句；記下每幀超過 8.3 ms（低於 120 FPS）的幀，依各計時器在其中花的時間排序。

| 版本 | 超過 8.3 ms 的幀 | 主要變化 |
|---|---:|---|
| Sched1E | 618 | 起點：換時段 25～34 ms（十人同一幀）、群眾逐幀更新 175 次 |
| Sched2E | 396 | 群眾元件位置沒變就不重設（逐幀更新只剩 18 次出現在卡頓幀）；動作檔改在背景讀 |
| Sched3E | 317 | 女主走路的路線分幀算（換時段最多 3 ms） |
| Sched4E | 247 | （計時）群眾的偶發卡頓全是臉部頂點計算：一次 3.6 ms |
| Sched5E | 2257 | 同時段 TTS session 的 GPU 實驗佔滿顯卡（95～97%），整體慢一截，不列入比較 |
| Sched6E | 173 | 臉部頂點平行計算（A/B：每次 4.3 → 2.0～2.3 ms）、碰撞方塊空間索引 |

- **臉部頂點平行計算**（`KKRuntimeRenderMesh.cpp` `EvaluateFaceVertices`，`ok.Face.Parallel`）：每個頂點互不相干，分塊交給 task threads；同一場遊戲交替開關各 60 秒比較，每次臉部更新 4.3 ms → 2.0～2.3 ms。
- **碰撞方塊空間索引**（`OKStreetSocialRules.h` `OKStreetBlocksIndexed`）：`OKStreetBlockedPoint`／`OKStreetObstacleGap` 每次都掃全部執行期方塊、還重建一次內建擺設清單；改成 5 m 分桶（每幀用 checksum 檢查方塊有沒有變，變了才重建），最近距離由近而遠一圈圈找，結果和原本相同。路線搜尋、路徑點檢查、走路間距都用它（22 處）。
- 診斷：`ok.Crowd.LogSlowEntries 1`（角色更新超過 1 ms 時分段記錄）。

### 群眾臉部頂點移到背景（Sched11E）

- `OKUpdateRuntimeMouthStream`（`KKRuntimeRenderMesh.cpp`）：輸入檢查留在 game thread（不合法的請求照舊讓呼叫端失敗），頂點計算交給一條依序執行的 task pipe（`OKRuntimeFacePipe`，舊的臉不會蓋過新的），算完直接排 render command 上傳，最多晚一幀。`ok.Face.Async 0` 可切回同步比較。

### 女主相遇、歷史紀錄、ok-mind 記憶（Sched14E–17E）

- **相遇**（`Encounter`）：原本複製兩次整個 store（一份改、一份 commit），改成直接修改後交給存檔工作；旁聽到的對話結果只重建字幕與紀錄（`RefreshUI(Bottom|History)`），不重建整個右側面板（那一幀原本 16 ms）。
- 細分後發現，一對女主相遇 5–9 ms 幾乎都花在規則效果的 `observe`（寫她的記憶）：
  - **歷史紀錄**（`HistoryAdd`）：每一行都在 game thread 上建資料夾、開檔、附加、關檔。改成交給存檔工作附加（`OKStreetAppendQueued`：同一個檔案還在排隊的行合在一起寫，順序不變）；讀回或改寫歷史檔之前（第一次載入、galgame 回滾、自我測試清理）先 `OKStreetFlushSaves`。
  - **ok-mind 記憶**（`Memories::persist`）：每加一則記憶就在呼叫端把她整份記憶序列化。寫檔佇列改成可以排「到時候再產生內容」的工作（`store::write_with`），記憶檔由寫檔執行緒取當下的內容序列化；同一個檔案還在排隊的舊工作會被新的取代。
- 效果：`EffectObserve` 5.2 → 3.4 ms（歷史紀錄）→ 不再出現在卡頓幀；`EncounterPair` 4–9 ms → 1.6 ms。galgame 回歸 9 項全過。
- 新增計時：`EncounterListeners／Rumors／Eval／Apply／Effects／Flush`、`Effect{Observe,Note,Rumor,Bond}`、`GridPull`、`TraceShot／TraceOverlap`、`RequestOverheard`。

### 道具延後刪除、ok-mind 鎖（Sched18E–19E）

- **道具刪除**：刪除一個道具 actor 約 1.6 ms（元件註銷、render／physics 狀態拆除），一個姿勢結束時六個道具在同一幀刪掉，`TickLife` 一幀 10 ms。新增 `DestroyLater`：先隱藏、關碰撞與 tick，再由 `TickDestroyQueue` 每幀最多花 1 ms 刪除（至少一個）。改用它的地方：生活姿勢、同行、環境道具、拍照特效、公司地塊、配對與設施道具。Sched19E 的卡頓幀不再出現 `TickLife`。
- **ok-mind 記憶寫檔**：寫檔執行緒在鎖內序列化，game thread 同時加下一則記憶時要等它；改成鎖內只複製她的記憶，放開鎖再序列化。
- 新增計時：`MindRemember`、`HistoryAdd`、`PlanAlternative`、`BlockPay／BlockPlace／BlockQueueWalk`。女主換時段剩下的 3–4 ms 幾乎都是打工結束時寫記憶（`BlockPay` → `MindRemember` 約 3 ms），下一步查 ok-mind 第一次讀她記憶檔的成本。

### ok-mind 預先載入記憶檔（Sched21E，整合後的 Base1025b）

- 一位女主在這一局第一次寫記憶時，ok-mind 要先在呼叫端讀取並解析她的記憶檔（約 3 ms，女主換時段時的 `BlockPay`→`MindRemember`）。現在 `Mind::open` 另開一條執行緒把資料夾裡的記憶檔都先讀好（`Memories::preload`，解析時不持鎖，已被打開的女主保留現有內容）；Sched21E 的卡頓幀不再出現 `MindRemember`。
- 結束對話（`FreeTalkLeave`）各段補計時：`LeaveParty／Photo／Facility／Outing／Companion／EndTalk／Close／Ui`。

### 規則計算移到背景執行緒（Sched22E–23bE）

- `TickAcademics` 每個遊戲分鐘一次，`AcademicsEval`（規則 DLL `campus_tick`，連同兩邊的 JSON）每次 2.3 ms。新增 `OKRulesEvalAsync`（`OKStreetSocialRulesGlue.inl`）：請求在 game thread 組好，交給 thread pool 計算，答案回到 game thread 再套用；scene state 最後在 game thread 釋放（裡面有 Slate 元件）。同一時間只有一個 `campus_tick` 在算（`AcademicsInFlight`），這段時間經過的分鐘併進下一次的 elapsed。Sched23bE 的卡頓幀不再出現 `TickAcademics`。
- `FOKStreetRules` 加讀寫鎖：`Eval` 可以在任何執行緒呼叫（Rust 那邊本來就是 `RwLock` 加 thread-local 錯誤），`Reload`／`Close` 會等正在算的請求做完；`OpenWith` 換 handle 時不再呼叫 `Close()`（Reload 已經持鎖）。
- 新增計時：送出對話前女主狀態的各段（`StatusBias／Menu／Scene／Invite／Heard／Today`）。

### render 端：來源材質命令快取被立繪擷取清掉（Sched26E）

- 量測：`profilegpu` 在四個地點的 GPU 幀時間都只有 2.7–3.1 ms；沿路線錄 Insights trace（`trace.file … cpu,frame`），各地點平均 138–289 FPS（game 約 4 ms、render 3–4.5 ms、GPU 2–6 ms）。GPU 不是瓶頸；「等 render 端」的慢幀是 render thread 本身在等（CPU Stall - Wait For Event 平均 4.7 ms）。
- 原因之一：`FLateSourceDepth`（不透明物之後補畫來源 IBL 材質的深度與顏色，`PostOpaqueExtensions`）的命令快取以 `FMeshBatch*` 為鍵，每畫一個 view 就把這個 view 沒畫到的項目刪掉。立繪擷取（只顯示一位女主，30 Hz）和主畫面共用快取，兩邊輪流把對方的項目刪掉再重建，render thread 上 6–7 ms。
- 修正（`OKSourceMaterialMesh.cpp`）：項目記下最後使用的幀，600 幀內沒有任何 view 用到才刪；位址被重用時，原本就會比對的 proxy、VF、材質等欄位會讓它重建，不會拿舊命令畫新物件。
- Sched26E：以等 render 端為主的慢幀 180 → 26，render thread 的 CPU Stall 出現在 164 → 8 幀；同一路線的卡頓幀 387 → 281。galgame 回歸 9 項全過。

### 玩家導航分幀與內建擺設索引（Sched28E–30E）

- Sched30E：`PlaceRoute` 不再出現在卡頓幀，`TickNavSearch` 最多 3.0 ms；三次導航都規劃出路線。galgame 回歸 9 項全過。

### 路線拉直分幀、聲音資訊只重建右側（Sched33E–34E，2026-10-26）

- 格子路線找到後的拉直（`GridPull`）一條長路線一幀 10.6 ms：每個候選轉角都要沿線測格子與一次膠囊 sweep，而且從最遠的格子往回試。改成和 A* 一樣分幀（`FOKStreetGridSearch` 的 Phase 3、`Path`、`PullI`、`PullJ`）：時間到了記下目前的轉角與下一個要試的格子，下一幀接著做。
- 女主的聲音資訊與「卡片已有聲音」回來時原本要求整個 UI 重建，改成只重建右側面板；卡片聲音沒變就不重建。
- 單幀卡頓的細分計時：`PartyLeaveMind／PartyLeaveUi`、`TraceOverlapMove`、`BlockIndexRebuild`、`PropIndexBuild`、`OKCrowd_SpeechBegin／SpeechAction／SpeechPlay`、`BlockPayNet／BlockPayObserve`、`LifePlay／LifeProps／LifePrewarm／LifeRainStart`、`CommuteLift`；銷毀佇列裡單一 actor 超過 3 ms 記 `Street destroy slow`，game thread 上同步規則超過 2 ms 記 `Street rules slow`（hitchprof 的輸出會彙整）。
- Sched33E／34E：卡頓幀裡不再出現 `GridPull`、`TraceOverlap`、`LeaveParty` 與群眾語音開始；同步規則超過 2 ms 的只有 `place_open`、`scratch_who` 各一次（2.1–2.5 ms），不是主要成本。galgame 回歸兩輪都 9 項全過（女主 1）。
- 仍會出現的一次性單幀（各 7–10 ms，每輪出現的項目不同）：送出對話（`PrepareFreeTalk` 約 6 ms，其中 `FreeTalkMindStatus` 3 ms、`JudgeContext` 1.6–2 ms）、她的回覆（`MindResult` 約 7 ms，`FinishTalkJudge` 3.5–4 ms）、換時段（`ScheduleBlockChange` 最多約 10 ms）、銷毀佇列裡單一 actor 約 10 ms、到達後搭電梯。
- 卡頓幀總數受機器上其他程序影響很大（Sched33E 321 幀、Sched34E 684 幀，後者最慢的幾幀 100–160 ms 都不在任何遊戲計時裡），比較改動只看各計時器。
- **約 10 ms 的一次性單幀多半不是程式本身**（Sched35E）：每輪都有幾個不同的段落各出現一次約 10 ms（`BlockPay` 10.8、`LeaveParty` 9.8、`ShopJobs` 10.3、群眾語音開始 10.8、商店面板重建 10.6），但它們底下的細分計時都沒有對應的耗時；同一段 `BlockPay` 在 Sched34E 只有 2.3 ms（其中寫記憶 1.5 ms）。量測時機器上同時有別的遊戲、Editor 與 ok-tts，系統可用提交記憶體常只剩二三十 GB：game thread 被系統排程讓出一個時間片（約 10–15 ms）或分頁時，落到哪段計時就算在哪段。這類幀要在沒有其他重負載的機器上量才有意義，不再逐段追。
- 還能從程式上減的一次性成本（各 2–6 ms，排在真實遊玩發現的問題之後）：送出對話時組 prompt（`PrepareFreeTalk`）、她的回覆裡的 judge 請求組裝（`FinishTalkJudge`／`JudgeContext`）、少數同步規則偶爾 2–3 ms（`bonds_tick`、`auto_friendship`、`place_open`、`scratch_who`）。
- 回歸女主改用 1：女主 3 被同樣的問題問了很多輪，一開口就結束對話，rollback 無從測起（她記得之前的回合）。

### 目前剩下的卡頓幀由什麼主導（Sched25E）

把每個超過 8.3 ms 的幀，依 game thread 最上層哪一段佔最多來分（scratchpad 的 `hitchsplit.lua`）：

| 主導的部分 | 幀數 | 平均 |
|---|---:|---:|
| 等 render thread／GPU（Frame Sync） | 180 | 6.3 ms |
| 沒有單一部分超過三成（整體略超過 8.3 ms） | 181 | — |
| Slate | 14 | 3.5 ms |
| 街區場景的 tick（我們的遊戲邏輯） | 8 | 7.5 ms |
| GC | 4 | 6.7 ms |

遊戲邏輯主導的卡頓只剩 8 幀，都是一次性的（送出一句對話、她的回覆、整個右側面板重建、玩家點導航）。接下來要再降幀數，主要在 render 端（render thread 與 GPU 的負擔），不在 game thread。

### 群眾動作串流開始（Sched24E–25E）

- 每次有人開始一段串流動作，game thread 會把角色的姿勢請求（骨架快照，數 MB）連同該動作的曲線整份複製一次：`StreamCopyRequest` 平均 3.3 ms、最多 4.7 ms，佔串流開始（`StreamStart` 4–9 ms）的大部分。
- 改成：`PoseRecipe` 存為共用且不再修改的 `TSharedPtr<const FKKRuntimePoseRequest>`；動作曲線另存一份共用的（`CurvesShared`，讀檔的 worker 一起做好）；`OKPrepareRuntimePoseBankAsync` 新增可傳入「產生請求的函式」的版本，請求在 worker 上組裝。
- Sched25E：`StreamStart` 1.4 ms；12 次串流動作都正常裝上。同一條路線的卡頓幀 387 幀，是這一系列量測中最少的（這輪機器上沒有其他 GPU 工作）。galgame 回歸 9 項全過。

### 自動成為朋友的檢查（Sched12E）

- `TickAutoFriendship` 原本每幀把每位陌生女主的關係送進規則（`auto_friendship`）一次，合計約 1.2 ms／幀，出現在 69 個卡頓幀裡。改成每幀輪流問一位（`AutoFriendshipNext`），每位大約每 10 幀輪到一次；Sched12E 的卡頓幀裡已經不再出現它。

- **換時段分幀**（`TickSchedules`）：一次 tick 換時段用完 2 ms 就停，其餘女主下一幀接著換。
- **路線分幀**（`FOKStreetGridSearch`、`GridSearchStep`、`QueueHeroineWalk`、`TickRouteJobs`）：路線第一次走過沒測過的街道時，每個 40 cm 格子都要一次物理測試，單條路線就 20～37 ms。格子 A* 改成可暫停的搜尋，女主換時段的走路每幀合計算 2 ms，找到就出發；找不到照舊直接放到目的地（離開房間則放到門口並放行）。玩家自己的導航仍一次算完。
- **群眾元件位置**（`OKCrowdSetTransform`）：每個角色每幀對 5～6 個元件 `SetWorldTransform`，就算站著不動也會重算邊界、標記 render transform；改成位置變了才設。
- **動作檔背景讀取**（`ClipBytesReady`）：第一次串流某個動作時讀檔改在 worker，請求等檔案到了再準備。
- 每批改完都跑 `Tools/galgame_regression.lua`，9 項全過。
